## Где закончили: вкладка «Ручная модерация»

Полностью переработана существующая вкладка настроек Telegram-чата, без нового экрана и боковой навигации.

Текущий UX:

- четыре закрываемых аккордеона; повторный клик закрывает открытый раздел, одновременно раскрыт максимум один;
- группы: «Предупреждения», «Ограничения», «Блокировки», «Исключение из чата»;
- справа от названия каждой группы находятся отдельные полупрозрачные голубые бейджи соответствующих команд (`/warn`, `/unwarn`, `/mute`, `/unmute`, `/ban`, `/unban`, `/kick`);
- внутри группы команды переключаются вкладками и имеют независимые настройки;
- по умолчанию при первом открытии страницы раскрыты «Предупреждения» и активна `/unwarn · Снять`;
- над аккордеонами расположен один общий тоггл «Автоматически удалять команды бота» для всех семи команд в текущем чате; под ним нет списка команд и нет разделительной линии;
- общий тоггл технически хранится в существующих command profiles, но `normalizeCommandProfiles()` синхронизирует `deleteCommandMessage` для всех семи профилей, а обработчик использует синхронизированное значение;
- у каждой команды отдельные получатели уведомлений `TARGET`, `PUBLIC`, `MODERATOR`, отдельные toggle и шаблоны;
- выключенный получатель скрывает редактор и предпросмотр; синяя рамка показывает редактируемого получателя;
- переменные отображаются кнопками и вставляются в позицию курсора; `%admin%` и `%target%` в Telegram становятся кликабельными;
- настройки удаления сообщения, на которое ответили, независимы для каждой команды;
- `/mute` и `/ban` имеют вложенную опасную настройку массового удаления сообщений пользователя, отдельное подтверждение и отчёт об успешных/неуспешных удалениях.

Логика `/unwarn`:

- поддерживает `/unwarn @username`, `/unwarn @username 2`, reply `/unwarn`, reply `/unwarn 2`;
- количество — только целое число от 1, по умолчанию 1;
- нельзя снять больше активных предупреждений, чем есть; действие не начинается и модератор получает понятную ошибку;
- `%amount%` — фактически снятое количество, `%warns%` — остаток, `%warns_limit%` — лимит.

Ключевые файлы:

- `src/components/manual-moderation-settings.tsx` — аккордеоны, вкладки, уведомления, общий тоггл, modal подтверждения;
- `src/app/automod.css` — стили карточки, бейджей и компактных секций;

## Ключевые архитектурные решения, которые нужно уважать

1. **Multi-tenancy добавлена поверх старой single-tenant модели, не заменяет её.** `AdminUser.role` (глобальная роль) — для email/password операторов, видят всё. `AdminUser.scope: "CHAT"` — самостоятельно зарегистрированные через Telegram владельцы чатов, видят только свои чаты через `ChatAdminAccess`. Для CHAT-scoped `role` всегда инертный `"VIEWER"`, реальные права — только через `resolveEffectiveChatRole(admin, chatId)` (`src/server/auth/guards.ts`).
2. **`ChatAdminAccess` (веб-панель) и `ChatRole`/`ChatMember` (права на команды бота внутри Telegram) — две независимые системы.** Не путать и не пытаться объединить — разный смысл, разные потребители.
3. **`requireChatAccess(admin, chatId)` возвращает честный 404, не 403** — chat-scoped админ не должен уметь отличить «чат не мой» от «чата не существует». Этот паттерн используется везде, где раньше проверялась только глобальная роль.
4. **Каждый новый `AuditLog`-action нужно вручную добавлять в вайтлист `journal-service.ts`** (`JOURNAL_ACTIONS`/`SETTINGS_ACTIONS`) — иначе строка есть в БД, но никогда не покажется в «Журнал». Забывали дважды за сессию, ловили только на ревью.
5. **Миграции пишутся руками** (`prisma migrate dev` недоступен без живого Postgres) — смотреть 2-3 последних файла в `prisma/migrations/` для стиля (без down-migration, явные имена constraint'ов).
6. **Сеть в песочнице (эта среда) нестабильна для Prisma CLI** (`prisma migrate deploy` регулярно падает с `Connection terminated unexpectedly`/`P1002`), но **обычный `pg`-драйвер работает надёжно**. Рабочий обход: применять миграцию вручную через короткий Node-скрипт на `pg` (открыть соединение, выполнить SQL, записать bookkeeping-строку в `_prisma_migrations` с sha256-checksum файла) — сработало во всех случаях. CI на чистом Postgres всегда проходил зелёным даже когда локальные тесты в песочнице падали с той же сетевой ошибкой — **CI считать авторитетным**, не гнаться за локальным зелёным прогоном в этой среде.
7. **Публичный `/commands`** (справка по командам бота) намеренно остаётся публичной страницей без логина, но теперь показывает сайдбар залогиненным админам (`getCurrentAdmin()` без редиректа, единственное такое место в кодовой базе).

## #124 — упрощение уведомлений модерации (детали)

Полный аудит уведомлений модерации (артефакт был опубликован пользователю) выявил кучу несогласованностей. По итогам сделано:
- Убрано приватное DM-уведомление при наказании (warn/mute/ban), остаётся только ephemeral-сообщение в чате (видно только наказанному).
- **Важное следствие**: `/appeal` раньше матчился на наказание через `metadata.appealDmMessageId === replyToMessageId` — ID того самого DM. Без DM это физически ломается (ephemeral-сообщения к тому же всегда `message_id=0`). `/appeal` переписан без Reply — сам находит последнее наказание (`appeal-service.ts::listAppealCandidates`/`submitLatestAppeal`), с числовой дизамбигуацией как у `/unmute`, если наказаний в нескольких чатах.
- Причина у warn/mute/ban/kick стала необязательной (`requiresReason()` в `moderation-service.ts` теперь всегда `false`). Причина при удалении сообщения — отдельное действие, не тронуто, по-прежнему обязательна.
- Апелляции — тумблер + настройки уведомлений на уровне чата (новая таблица `ChatAppealSettings`, без глобального профиля-наследования — как `ChatAdminAccess`, не как `captcha`/`manual-moderation`), тексты вынесены в редактируемый набор (новая `GlobalAppealSettings`, поверх той же UI-страницы «Система → Уведомления»).
- «Снять предупреждение» добавлено в Web Admin (`executeAdminWarningRevoke`, раньше — только команда `/unwarn` в чате).
